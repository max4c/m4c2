A year ago I wrote [How to Build with AI](https://maxforsey.com/blog/how-to-build-with-ai). The core ideas — context is king, micro loops over mega prompts, every person is a manager now — still travel. But I want to grade myself, because the world moved fast and a few of those framings now feel small.

**"Every person is a manager now" undersold it.** A manager delegates one role. What I'm actually doing every day is product work, design work, and engineering work — at the same time, on the same task, often inside the same prompt. The agent does the typing. I do the rest.

**"Avoid mega prompts" inverted itself.** I now write mega prompts on purpose, save them as skills, and run them on demand. The thing I was warning against became my unit of leverage.

**The tool list is dead.** Cursor agent mode and Lovable were the right answers in April 2025. They aren't now.

This post is the update. It's about how my coding has changed, what changed it, and where I think it's going next.

### Spiky agents, whole humans

Andrej Karpathy describes today's models as **spiky intelligence** — jagged, brilliant in some places, surprisingly dumb in others. They write a thousand lines of working Swift in five minutes and then misread a button label. They one-shot a complex refactor and then quietly delete a test you needed.

The honest implication is that *you* have to be the part that isn't spiky. Where the agent is sharp, you delegate. Where the agent is dull, you compensate. Compensating is product thinking, design taste, system instincts, and the patience to verify. There is no role you get to skip — the agent has the spikes, so you have to be the curve that smooths them out.

This is why "manager" was the wrong frame. A good manager has subordinates who are competent across all the dimensions of their job. An agent isn't competent across all dimensions; it's competent in narrow strips and confidently wrong in others. The job isn't to delegate. The job is to be everywhere the agent isn't.

### The progression

It starts with an editor and ends with an orchestrator. Most of my friends are somewhere in the middle.

### Past: figures 1–4 — the IDE era

Figure 1 is the old world: an editor, a file tree, a human typing. Figure 2 adds a coding agent inside the editor that asks for permission on every change. Figure 3 is YOLO mode — auto-approve everything, hope for the best. Figure 4 is what Cursor and others have evolved toward: a more structured agent UI inside the IDE, with sensible YOLO defaults.

I lived in figures 2 and 3 for most of last year. Cursor agent mode was great. It's also still evolving — they have a new interface that goes beyond the IDE — and I don't want to dunk on a tool that helped me ship a lot of work. But for me, the shape of the IDE itself became the bottleneck. I kept hitting cases where I wanted my agent to live somewhere bigger than a sidebar, and where I wanted to run several at once without juggling editor windows.

### Present: figures 5–7 — the terminal era

Figure 5 is one Claude Code or Codex instance running in a terminal. Figure 6 is a few. Figure 7 is many.

This is where I live now. My setup:

- **[Ghostty](https://ghostty.org/) + [Codex](https://github.com/openai/codex)** as my primary stack. Ghostty is GPU-accelerated and stays out of my way. Codex handles most of the work; Claude Code handles the rest.
- **tmux panes** so I can keep five or six agents running on different tasks without losing my orientation.
- **A folder of skills** I've built up over the past few months.
- **[lazy-agent](https://github.com/runpod/lazy-agent)** to get the terminal environment right in the first place.

A few of these deserve their own paragraphs.

**Skills are codified clarity.** A skill is a markdown file that tells the agent how to do a recurring task you care about. I have `/insights` for distilling notes, `/simplify` for clean-up passes, `/design-interface` for UI sketches, and `/review` for verification. My favorite is `/grill-me`, which I originally adapted from [Matthew Pocock](https://x.com/mattpocockuk)'s version and then rebuilt around how I actually plan posts and tickets. It's the one I was running while writing this paragraph. Skills are how I stopped re-typing the same instructions and started reusing them. They're also why "avoid mega prompts" is dead — a skill *is* a mega prompt, but it's a mega prompt I trust because I've refined it over many runs.

**Lazy-agent is the easiest on-ramp I've seen.** It's pitched as "LazyVim, but for terminal-based AI agent workflows," and that's basically right. It set up Ghostty, Zsh with Powerlevel10k, tmux, and Claude Code integration in an afternoon. More importantly, it taught me tools I would have otherwise ignored — [zoxide](https://github.com/ajeetdsouza/zoxide) is the cleanest example. I'd been resisting changing how I `cd` for years. After two days with `z`, I can't go back.

**Bugbook is where my agents and I share a workspace.** Bugbook is the local-first tool I'm building for myself: notes, databases, terminal, mail, calendar, AI sidebar, Agent Hub, all in one window. The reason it matters here is that my agents have a CLI (`bugbook page`, `bugbook db query`, `bugbook agent task create`) that reads and writes the same data I do. They file tickets. They update specs. They log runs. I'm not soft-launching the product — I'm telling you that once you have this many agents running, you start needing a workspace they can talk to instead of a chat history they live inside. [cmux.dev](https://cmux.dev/) is in the same neighborhood; I tried it but it was buggy when I tested it.

### Future: figure 8 — orchestration

Figure 8 is one orchestrator dispatching many Claude Codes. This is where I'm headed and where I think the edge of the field is right now.

Two bottlenecks force me here.

**Review at volume.** I have a strong CI/CD pipeline. I have a `/review` skill. I use Codex for second-opinion review. I use agent-browser, Claude computer use, and Codex computer use to verify visual changes. None of that is the problem. The problem is that when six agents finish their work in the same hour, *I* become the bottleneck — manual spot-check, taste judgment, cross-cutting concerns that no individual agent has visibility into. The fix is going to look like agents reviewing each other under explicit trust gradients, with human review compressed onto the highest-stakes diffs. I haven't built this yet.

**Context-switching.** Even when review is fast, watching five terminals while reasoning about the meta-task is taxing. I want a single pane of glass — a dashboard, an orchestrator-level chat — where I'm directing the swarm rather than peering into each window. Bugbook's Agent Hub is a stab at this. It isn't enough yet.

The interesting work in this space:

- **[Paperclip](https://paperclip.ing/)** is the most direct attempt I've seen at orchestrating coding agents from the outside.
- **Steve Yegge's [Welcome to Gas Town](https://steve-yegge.medium.com/welcome-to-gas-town-4f25ee16dd04)** is the essay to read on what this future actually feels like — agents running unattended overnight, the human checking in at dawn.
- **[Factory.ai](https://factory.ai/)** is in the orchestration conversation. I haven't tried it.
- **Conductor** I tried and bounced off at first. Worth another look.
- **The Claude Agent SDK and Cursor Agent SDK** are where I'll likely end up building my own orchestration, because at some point the off-the-shelf tools won't fit the specific shape of work I do.

This is the part of the post I'm least sure about, which means it's the part where I'm most actively building.

### The thread underneath: clarity before commit

Step back from the progression for a second. The actual skill that has compounded for me — across every figure, every tool — is **clarity before commit**.

Spec-driven development is the practice. I don't start a non-trivial task without a spec. `/grill-me` exists to get the spec right before I write a line of code. `/design-interface` exists to lock the shape of a UI before I start asking an agent to build it. The reason this works is simple: the agent is fast, but it can't read your mind, and it certainly can't tell you when your idea is incoherent. You have to do that part.

Here's something I realized while planning this post: I've been investing in clarity at the *front* of the loop — specs, prompts, skills. I've been under-investing in clarity at the *back* — review. Yes, I have a `/review` skill. Yes, my CI/CD is strong. But I've been treating review as a smaller, less interesting problem than spec-writing, and that's wrong. The orchestration bottleneck I described above is fundamentally a review problem. Six agents producing six PRs isn't a coding problem — the code works. It's a verification problem. And verification deserves the same rigor I give to specs.

If I had to compress the entire post into one line: **clarity at both ends**. Specs going in. Verification coming out. Everything else is plumbing.

### What I think you should do

I'm not going to tell you to install Claude Code, even though I think you should. I'm not going to tell you to build a skill, even though that's the lowest-friction way to feel the new workflow. The thing I actually want you to do is harder and more useful:

**Audit your own spikiness.** Where is your weakest dimension? Is it product — do you ship features nobody asked for? Is it design — do your interfaces look like a backend engineer made them? Is it engineering — do you depend on agents to write code you couldn't review if they got it wrong? Is it agent-handling — can you keep one agent productive but not three?

Pick one. Widen there. The agents will keep getting sharper at the spikes; your job is to be the curve.

If your weak dimension is design, [cosmos.so](https://cosmos.so/) is a good feed for visual taste, and I'm looking into [Mobbin](https://mobbin.com/) for product patterns. If it's product, write more specs and grill them harder. If it's agent-handling, set up [lazy-agent](https://github.com/runpod/lazy-agent) this weekend and start running two agents in parallel on the same project. If it's engineering, pick a system you usually let agents own and rebuild it from scratch yourself.

The shape of "good at building" is changing fast. A year ago it was "knows the right model for the right step." Now it's "is whole enough to be the part the agents aren't." A year from now it will be something else, and I'll write that post too.
